## Flask API


### Backend session endpoints

- `POST /api/v1/auth/session`: send `Authorization: Bearer <Firebase ID token>` and `Content-Type: application/json`. The body is `{}` or an object with optional nonempty `name` (up to 100 characters), `city` (100), and `favorite_sport` (50).
- The backend creates missing `users/{uid}` and `profiles/{uid}` records in one transaction. It assigns `player`/`active` defaults and takes email from the verified token. Repeat calls preserve existing data; profile edits will use the future profile endpoint.
- `GET /api/v1/me`: use the same bearer header to read the current account without creating records. Both endpoints return `{ "user": {...}, "profile": {...}, "role": "player" }`; timestamps currently use Flask's HTTP-date JSON representation. A new profile has a `null` reliability score until scoring is implemented.
- Missing/invalid tokens return 401, suspended accounts return 403, missing account setup on `/me` returns 403 `PROFILE_REQUIRED`, invalid session input returns 400, and unavailable authentication/database services return 503. Retrying session setup is safe.
- Flutter now calls session setup after sign-in and session restoration, attaches the Firebase ID token, and validates that returned user/profile IDs match the signed-in identity. A 401 triggers one token refresh and one repeat request; network/server failures offer explicit retry. Token acquisition and each HTTP exchange have a 20-second timeout. Requests without a token are rejected locally.
- Live mobile-to-API access, Firestore persistence, and concurrent transaction behavior still need integration verification. An existing Xcode build without `API_BASE_URL` configured will need the address supplied before its next integration build; configuration is compiled into the app. Prefer a reachable HTTPS dev API for phone testing.

Run local backend checks from `services/api/` without production credentials or database writes:

```sh

```

### Profile setup

After session setup, profiles without `setup_complete: true` enter username and sport selection.
Authenticated `GET /api/v1/usernames/availability?username=...` returns availability; it does not reserve the name.
Authenticated `PUT /api/v1/me/profile` accepts only `username` and a nonempty `sports` list.
The server transaction reserves `usernames/{lowercase_username}` for the verified UID and updates the profile together.
A competing claim returns 409 `USERNAME_TAKEN`; retries by the same owner are safe.
Existing completed profiles skip setup. Photo uploads and extended profile editing are not yet implemented.

### Location setup

After username/sports setup, users without saved coordinates choose GPS or a manual area. Manual lookup uses Geoapify Autocomplete with a compiled-in `GEOAPIFY_API_KEY`; GPS can still succeed without this key, showing coordinates when reverse geocoding is unavailable. The app requests only foreground location on explicit user action. No position stream or background tracking is started.

`PUT /api/v1/me/profile/location` accepts `latitude`, `longitude`, `label`, and `source` (`gps` or `manual`). It verifies Firebase identity, rechecks profile completion and suspension within the transaction, and stores a Firestore GeoPoint plus label/source. Account responses serialize GeoPoints to latitude/longitude JSON.

The installed geolocator 14.1.2 package supports Android/iOS and uses the MIT license. Added Android internet/coarse/fine location declarations and iOS when-in-use purpose text. Native compilation/permission dialogs need verification at the next device checkpoint. For SPM distribution builds, follow the plugin's documented `BYPASS_PERMISSION_LOCATION_ALWAYS=1` build environment setting; no background capability is enabled. Do not manually patch generated packages.

Official references: https://pub.dev/packages/geolocator and https://apidocs.geoapify.com/docs/geocoding/address-autocomplete/

## Profile photos and setup motion

Profile photos use the system gallery picker (`image_picker`) and the protected backend endpoint `GET/PUT/DELETE /api/v1/me/profile/photo`. Install current API requirements before restarting the local server; Pillow handles image validation and metadata removal. The client sends a resized selection as JSON (`image`: base64 bytes); the server accepts at most 2 MiB, normalizes a square JPEG, and stores only a thumbnail capped at 128 KiB in `profiles/{uid}/media/avatar`. Session/profile responses do not include the image. Reads and mutations require the verified owner's active account, with no public file URL or client-side Firestore writes. This bounded avatar implementation needs no Storage bucket; full-size/general media storage is outside its scope.

iOS includes the photo-library purpose description; Android uses the system picker without broad storage permission. Cancel does not upload. Preview requires explicit confirmation, failures retain the previous photo, and Android recovered selections require review. After a native rebuild, verify gallery access and HEIC images on a physical iPhone, replacement/removal, retry while offline, and persistence after signing out/in. These device/database integration checks have not yet been completed.

Setup progress is centered above its action, with sign-out in Profile. Setup transitions and map recentering respect Reduce Motion. Recenter targets the saved area and is interrupted by map dragging; it does not request a fresh GPS fix. Explore retains required map attribution in a compact line with full links in map info.

## Vercel backend deployment

The deploy root is `services/api`, not the repository or Flutter app. `index.py` exports the Flask app; `.python-version` selects Python 3.14. The local API continues to use `run.py`. Vercel configuration disables development debug mode. Vercel serves the API only; the Flutter app remains installed on the phone.

The preferred initial deployment path while Git operations are deferred is Vercel CLI, run from `services/api`. Authenticate with `vercel login`; do not deploy until the project, upload exclusions and environment are reviewed. `.vercelignore` allows only runtime sources/configuration. Do not drag the raw backend folder into a browser uploader: it contains local credentials and a virtual environment, and browser upload exclusions have not been verified.

Configure these project environment variables before functional deployment:
- `FLASK_ENV=production`
- `FIREBASE_PROJECT_ID=playerszwz`
- `FIREBASE_SERVICE_ACCOUNT_JSON`: complete JSON from the existing backend service-account file, stored as a sensitive server-side environment variable. Never paste it into chat, source, terminal commands or logs. Cloud JSON takes precedence over the local credential path and must match the project ID.
- `GEOAPIFY_API_KEY`: the existing Geoapify key. The API supplies it to installed mobile clients at runtime through `/api/v1/mobile-config`, so it must be restricted in Geoapify. It is not a server secret once map tiles are displayed.

Do not set the local `GOOGLE_APPLICATION_CREDENTIALS` file path on Vercel. Native apps don't require browser CORS origins. Firebase remains on Spark within its quotas. Review Vercel deployment protection so the mobile client can reach the production API while application endpoints continue to require Firebase tokens. Verify `/health`, unauthenticated `/api/v1/me` rejection, then authenticated session and profile/photo/location operations before changing the mobile API_BASE_URL. No deployment or cloud credential validation is implied by local tests.
